# 技术方案差异与改进清单

## 已对齐内容

| 要求 | 当前 GZ_0524/app 状态 |
| --- | --- |
| 故障库需要覆盖多类故障 | Main Demo 已包含全局故障库和演示故障实例 |
| 故障注入目标需要受模块能力约束 | 已通过模块能力和层级过滤控制可注入对象 |
| 故障设置应基于模块实际参数 | 属性面板已按当前模块声明的输入、输出、中间变量、参数生成 |
| 绑定对象应使用变量原名 | 故障实例绑定对象不再二次加工 |
| Python 模块需要可绑定 | 模型包已记录 `command_shaper.py` 绑定信息 |

## 主要差异

| 优先级 | 差异 | 风险 | 改进方向 |
| --- | --- | --- | --- |
| P0 | 模型包 schema 还未成为强制约束 | 新增模块时可能漏写变量或故障能力 | 增加 JSON Schema 与校验脚本 |
| P0 | 故障类型参数缺少统一 schema | UI 和运行时可能对参数含义理解不一致 | 每种故障类型声明参数字段、默认值、单位和范围 |
| P1 | Python 后端仍需要独立服务化 | 仿真链路无法完全验证真实 Python 函数 | 实现 `runtime/python-backend` 服务并接入前端 |
| P1 | 故障场景保存和版本管理不完整 | 难以复现实验和对比注入结果 | 增加 scenario schema 与保存、加载、撤销能力 |
| P2 | 故障传播矩阵未系统实现 | 多模块耦合故障只能局部模拟 | 建立注入矩阵、传播矩阵、输出矩阵 |
| P2 | UI 缺少批量配置和筛选能力 | 变量多时属性面板扫描效率低 | 改造成紧凑变量表和批量层级操作 |
| P3 | demo、runtime、authoring 仍混在 app 内 | 后续维护边界不清晰 | 拆出 runtime、packages、tools，保留 app 为界面层 |

## UI 改进方向

故障设置面板后续应优先解决扫描效率，而不是继续扩大卡片视觉重量：

- 用紧凑表格展示变量名、中文名、类型、物理层、电气层、协议层。
- 每个模块顶部显示故障能力摘要，例如可注入变量数、已启用层级数、活动故障数。
- 保存槽位、注入故障、删除模块应分组，危险操作保持 Carbon 风格的明确层级。
- 大量变量时提供搜索、按目标类型筛选和一键全选层级。
- 实例列表显示 `faultTypeId -> bindingObject`，让调试时能直接核对真实变量。
